# Contributing to ObsiFlow

Welcome to the **Data Quality & Pipeline Observability Platform (ObsiFlow)** repository. This project is developed collaboratively by a six-member university engineering team across six core disciplines:

- **Data Pipeline Engineering (`DE`)**
- **Data Quality Validation (`DQ`)**
- **Orchestration & Platform Reliability (`OR`)**
- **Observability & Telemetry (`OB`)**
- **Testing & Quality Assurance (`QA`)**
- **DevOps & Infrastructure (`DO`)**

These contribution guidelines ensure code quality, consistency, and a smooth collaborative development workflow across all team roles.

## Core Principles

- **No direct commits to `main`**: All changes must be introduced via topic branches and pull requests.
- **Small, focused changes**: Keep pull requests focused on a single logical feature, fix, or task. Aim for reviewable pull requests (ideally under 300–400 lines of change).
- **Never commit credentials or secrets**: Passwords, tokens, database connection strings, and local environment secrets must never enter version control.
- **Never commit generated artifacts or raw batches**: Test fixtures generated by `data/genration_script/generate_data.py` and local Airflow logs must remain uncommitted.

## Branch Naming Conventions

All branch names must be lowercase, use forward slashes for category separation, and use hyphens between words. Include the role abbreviation or task ID when applicable:

| Branch Category | Purpose | Example |
|---|---|---|
| `feature/` | New functionality or module | `feature/dq-null-checks`<br>`feature/de-batch-loader`<br>`feature/ob-prometheus-exporter` |
| `fix/` | Bug fixes or issue resolution | `fix/or-dag-retry-delay`<br>`fix/dq-schema-type-cast`<br>`fix/db-connection-leak` |
| `docs/` | Documentation additions or edits | `docs/update-architecture-overview`<br>`docs/setup-guide` |
| `refactor/` | Code refactoring without changing functionality | `refactor/validation-rule-dispatch`<br>`refactor/loader-idempotency` |
| `test/` | Adding or improving tests | `test/qa-reconciliation-tests`<br>`test/validator-edge-cases` |

### Branch Lifecycle:
1. Always update your local `main` branch before branching:
   ```bash
   git checkout main
   git pull origin main
   ```
2. Create your feature or fix branch:
   ```bash
   git checkout -b feature/dq-null-checks
   ```

## Commit Message Conventions

This project strictly follows the **Conventional Commits** specification. Each commit message must be clear, concise, and structured as follows:

```text
<type>(<scope>): <imperative subject line>

[optional body explaining motivation and context]

[optional footer referencing task ID or issue, e.g., Resolves DE-02]
```

### Allowed Types:
- `feat`: A new feature or capability.
- `fix`: A bug fix.
- `docs`: Documentation-only changes.
- `style`: Formatting, missing semicolons, whitespace (no code change).
- `refactor`: Code change that neither fixes a bug nor adds a feature.
- `test`: Adding missing tests or correcting existing tests.
- `chore`: Maintenance tasks, dependency updates, or configuration adjustments.

### Common Scopes:
- `extract`, `transform`, `validate`, `load`, `airflow`, `metrics`, `dashboards`, `generator`, `docs`, `config`

### Practical Examples:
```text
feat(validate): implement null value check rule family
fix(airflow): increase DAG retry delay to handle transient DB lock
docs(contributing): clarify branch naming and conventional commits
test(load): add idempotency verification test for re-running batches
chore(gitignore): ignore local airflow logs and pytest cache
refactor(transform): modularize date parsing into utility helper
```

## Pull Request Workflow

1. **Verify locally**: Before opening a pull request, run your local test suite and ensure that your code complies with `.editorconfig` rules.
2. **Push your branch**:
   ```bash
   git push origin feature/dq-null-checks
   ```
3. **Open a Pull Request**:
   - Target branch: `main`
   - Fill out all sections of `.github/PULL_REQUEST_TEMPLATE.md`.
   - Reference the relevant task ID (e.g., `DE-01`, `DQ-03`, `OR-02`) or issue number.
4. **Link Deliverables**: If the PR fulfills part of a milestone KPI, note which KPI is affected.
5. **Clean up**: Once merged, delete your feature branch locally and remotely.

## Code Review Expectations

All pull requests require **at least one approving review** before merging into `main`.

- **Reviewer Responsibilities**:
  - Review changes within 24 to 48 hours to maintain team velocity.
  - Verify that the logic meets the functional requirements and handles edge cases.
  - Check that no sensitive credentials, temporary files, or unnecessary dependencies are included.
  - Provide constructive, actionable, and courteous feedback.
- **Author Responsibilities**:
  - Address review comments promptly.
  - Avoid pushing unrelated changes to an open PR.
  - Re-request review once revisions are made.

## Testing Expectations

Reliability is a core pillar of this platform. Before submitting a PR:

1. **Unit & Integration Tests**: Verify all existing tests pass and write new tests covering your additions.
2. **Deterministic Data Generator Verification**: If altering schema expectations or validation bounds, run:
   ```bash
   python data/genration_script/generate_data.py --out /tmp/test_output --rows 100 --seed 42
   ```
   Confirm that the output generates without errors.
3. **Edge Case Coverage**: Test edge cases such as missing columns, invalid data types, empty datasets, and database connection timeouts.

---

## Documentation Requirements

- **Keep Documentation Synchronized**: When a pull request introduces a new rule family, modifies schema definitions, changes environment variables, or alters pipeline flow, update the corresponding documentation in `docs/` or `README.md` within the same pull request.
- **Code Comments**: Document public functions and modules with clear Python docstrings specifying arguments, return types, and exceptions raised.

---

## Clean Repository Hygiene

To keep the repository clean and secure:

- **No Secrets**: Never commit `.env` files, passwords, or tokens. Always use `.env.example` as a template with placeholder values.
- **No Generated Fixtures**: Generated batch data files belong in local directories ignored by `.gitignore`.
- **No Large Binary Dumps**: Database dumps, local SQLite files, and Airflow run databases must not be tracked in git.
- **Single Responsibility**: Do not mix reformatting with functional changes in the same commit.
